# EVM production review — 2026-09-11

The comprehensive review found and repaired reproducible correctness and operational defects that the earlier 376-test suite did not cover. The final canonical and Claude copies pass 420 EVM tests each; all five repository suites pass, 912 tests total. No remaining release blocker was identified in the reviewed and tested paths. This is evidence for shipping the bounded standard workflow, not a guarantee that every future token, provider response or model-authored conclusion is correct.

The user's non-negotiable constraint was preserved: no additional research steps, coordinator turns, lane turns, tool calls, presets, report reads or successful-path network requests. Fixes execute inside existing commands. The ordinary review still targets 5–7 minutes, with the existing stopping rules and 10-minute cap.

**Baseline and scope.** The checkout already contained substantial uncommitted performance and delivery repairs. A byte-preserving snapshot of that working tree—not HEAD—was taken before editing. Review covered entrypoint/runbook/lane consistency, collection and discovery, request/deadline accounting, restart behavior, source and identity boundaries, decoded facts, automatic findings, scaffold/compose/finalize/checkpoint/delivery, strict validation, frozen replay, release metadata, registrations and Claude parity. Three independent reviewers reproduced and evaluated bounded offline cases; subsequent passes reviewed the fixes themselves. No live token research, RPC requests, paid provider usage, package installations, commits or pushes were performed.

**Reproduced defects and repairs.**

| Area | Before | Reviewed behavior |
| --- | --- | --- |
| RPC retries | A collection capped at 4 requests made 6 transport calls while reporting and charging 4. Worker retries bypassed both ledgers and could run into time reserved for final header checks. | Each retry receives coordinator-owned authorization and counts against both limits. One retry remains available within the existing allowance and query deadline. Other pins' final-check reservations are preserved. Same-run failed-read reuse cannot open a new retry allowance. |
| Web requests | Retries and redirects were hidden behind one URL charge. Prepaid lanes could spend their allowance repeatedly across batches. | Every actual HTTP attempt consumes the existing shared session allowance or the lane's prepaid counter. The local counter persists across batches, including redirects/retries; exhausted and zero grants perform no requests. No additional charging tool call is needed. |
| Web deadlines and credentials | Late EOF could accept a response after its deadline; budget acquisition could leave a stale request timeout. Refused URL userinfo could remain in provenance. | One deadline bounds capture and retry processing, including checks after reads and budget acquisition. Error bodies are read in bounded chunks. Refused userinfo and credential-like query values are neither sent nor saved, including redirect destinations. Connections are closed. |
| Failed starts | Refusing an unrelated existing directory could mark it restartable. A legitimate restart archived the session and started a fresh request/deadline allowance. A provider preflight failure consumed the restart marker. | Only a start owned by this invocation and failed during chain/head acquisition gets a marker. Provider checks occur before mutation. Archived artifacts retain a snapshot, while the same live session/cache preserve identity, spent attempts, deadlines and ceilings. Target changes and already-pinned restarts are refused. |
| Sale interpretation | A token deposit into pool A plus an unrelated Swap in pool B could be a verified sale. The largest liquidity deposit could be mislabeled as the sale amount. | Decoding matches same-pool identity, Swap direction and exact target input amount to one unambiguous transfer. V4 additionally binds the event pool ID and qualifies its indexed currency association. Direct proceeds must match the pool output; routed proceeds remain unresolved. Pool identity evidence travels with the finding. |
| Missing reads and authority | Failed implementation/approval reads could become “zero”/“none.” A capped 20-address display could become a false 20-signer assertion. Reverts/no-code/getter shapes could imply absent functions, EOAs or identified Safes. | Successful zero words remain distinct from unavailable reads in facts, notes and scope. Owner-array ABI shape is validated and its full count retained separately from the display cap. Text describes observed code/getter behavior and leaves identity and guarded powers unresolved. Untyped numeric getters retain raw units. |
| Indexer evidence | Missing market fields could aggregate to zero. Wrong-shaped API data could abort processing. Creator transfers with missing asset identity or unrelated recipients could count as target activity. Unavailable creator pages could become observed zeros. | Invalid/missing metrics remain unknown; real zero remains zero. Invalid shapes and conflicting chain rows are excluded. Target activity requires exact asset/direction, and counters require a successfully parsed page. Neither unavailable creator page produces a factual activity finding. |
| Checkpoints and reporting | A focused/interrupted pipeline without coordinator judgment could fail on a nonexistent default summary finding, then on missing decision review. Instructions also pushed partial observations toward full coverage and required a fixed row count. | Internal checkpoints preserve actual gaps and concerns; they may omit unmade analyst judgments and remain undeliverable. Completed reports still require decision review and all existing gates. Guidance preserves supported observations alongside specific gaps, makes 8–12 rows an evidence-dependent target, and recognizes finalize's existing automatic delivery mark. |
