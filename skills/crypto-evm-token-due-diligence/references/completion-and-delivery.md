# Complete broad diligence efficiently

Target a completed ordinary broad review in **5–7 minutes end to end, 10 at most**,
including report validation. This is the default service target, not permission to omit
checks or turn uncertainty into a pass. An explicit user hard deadline controls.

**Standard scope.** A completed ordinary review is the standard scope executed to its
stopping rules: the `broad_collect.py` pipeline's four pinned phases and source match, the
two lane checklists in the lane briefs, and at most two coordinator presets. Feasible work
inside that scope is never deferred; work beyond it needs a named conclusion-changing
trigger (an unresolved seizure/mint/upgrade power, a withdrawal path over material
principal, a contradicted material claim, a user requirement that cannot otherwise be
evaluated). A run past 10 minutes states the trigger in one line before continuing;
otherwise it saves an internal checkpoint and the answer names what remains. The
completion gate still rejects `pending` and `not_checked` surfaces: each surface ends as
checked, affirmatively not applicable, or bounded by recorded attempts and an external
boundary. Do not start with a 45-minute plan or a uniform request allowance per surface.

## Schedule the critical work first

Use one fresh investigation, one coordinator-owned query queue/cache and two brief-driven
lanes as described in [source routing](source-routing-and-execution.md).
Plan the eleven **questions**, not eleven serial mini-audits or a tour of every website.
Assign each source and query one owner; share captures across lanes.

| Elapsed target | Work product |
| --- | --- |
| 0:00–0:30 | Read the provider policy excerpt; start `broad_collect.py start` in the background. |
| 0:30–1:30 | `discovery.json` exists: print both lane briefs and launch both lanes in one message. The pipeline continues to `facts.json`. |
| 1:30–3:30 | Read `facts`; `start` ran its recommended queue itself, so run only a row it deferred (at most four presets of your own) while time allows; compose them as they return. |
| 4:00–4:30 | Lane notes due; compose each. A lane that has not returned leaves its surfaces as recorded gaps. |
| 4:30–6:00 | Write the coordinator note (findings, all eleven coverage rows, decision, texts); `finalize`. |
| 6:00–7:00 | One repair round at most; write the chat answer from the frozen report. |

These are scheduling milestones; the 4-minute lane cutoff is a hard cutoff. Do not wait for all workers before
servicing a consequential request. Coalesce compatible queries already in the queue into
a small number of batches; preserve per-instance authority reads and pin rechecks. Avoid
one collection per getter and re-reading a source already captured by another lane.

Define finite evidence questions at intake. General diligence includes current custody,
material concentrations, launch integrity, bounded creator activity, delivered work and
actual holder economics. It does not silently become an all-time multi-wallet forensic
accounting engagement, a proof of human beneficial ownership or an audit of every external
issuer/bridge. Escalate those only for a concrete discrepancy, claimed entitlement or
conclusion-changing dependency. Preserve the full authority-discovery floor and all eleven
surfaces; scope the proposition precisely rather than claiming an unperformed full audit.

## Operational limits and exception handling

`broad_collect.py start` fills `work-plan.json` from the standard scope and reviews the
session before its later phases; edit the plan only when you add presets. Conservative tool
charges are not measured network request counts. The 5–7 minute target is the initial
end-to-end estimate unless a specific known architecture justifies an exception.
Finite request/deadline ceilings retain their user/provider/analyst provenance. A configured
paid key or a latency target never authorizes purchases, unlimited calls or relaxed checks.

Review the plan after architecture discovery, lane handoffs and before further batches:

- `continue`: execute useful queued work, using exact same-investigation cache hits.
- `replan`: explicitly revise the allowance in the same ledger inside existing ceilings.
  Replanning is recovery from a justified shortfall, not routine time renewal. Explain the
  specific new evidence problem; remove optional expansion first.
- `limit_review_required`: finish captured-evidence analysis and identify the actual
  remaining work and binding ceiling. Do not reset the ledger or rename pending work.
- `completion_review_required`: reconcile the evidence; this planning result cannot
  certify completion. Zero-request unfinished analysis is still work.

A timeout or malformed invocation is a failed operation, not an external fact. Correct
query/pin/flag errors within existing authorization. Import useful partial responses and
retry only the missing necessary queries, never an entire successful batch. Repeated
identical failure, a new deadline, a helper error or compaction does not make progress.

## Close the work, not just the report fields

Before closing each unknown, distinguish:

1. **Feasible operation:** run it now, including supported local calculation from saved
   evidence. Source matching, receipt decoding, journal reconciliation and current-state
   getters do not belong in a final list of useful additions.
2. **Missing convenient interface:** check the underlying permitted route. For LP/holder
   exports consider indexed events, manager/core positions and bounded RPC reconstruction;
   for source matching consider the supported comparison/compiler route. A failed UI/export
   does not establish an unavailable onchain fact. See [pool history](pool-history.md).
3. **External evidence boundary:** after relevant primary and permitted alternative routes,
   the source does not publish the audit/ledger/identity, access is unavailable, or the
   event is not yet observable. State the completed checks, missing fact and precise effect
   on the conclusion. An analyst's clock, local script failure or missing UI button is not
   such a boundary. Never invent a public report or identify an unknown owner to fill a box.

Keep one concise [stopping review](stopping-and-escalation.md) per affected surface. Record
actual methods and results, not a generic 'routes exhausted' sentence copied eleven times.
A worker's unsupported browser assertion must be checked against coordinator capabilities.
A complete review can contain unavailable facts; it cannot contain feasible research
handed back to the user. Do not claim full lifetime or protocol-wide coverage from samples.

## Incremental assembly and final delivery

Use the supported assembler throughout: the pipeline imports raw collections and registers
discovery captures; lanes' `web_capture.py` files are registered when a note cites them;
`bundle_assemble.py compose` expands notes; `finalize` runs check, freeze and deliver. Read
evidence through `bundle_assemble.py facts`, never raw JSON. Do not write a report-generation
script or weaken validators during research; every recurring assembly need belongs in the
maintained helpers.

The final `freeze` requires all eleven surfaces investigated or affirmatively inapplicable,
with no `pending`, `budget_exhausted` or untouched work. `--checkpoint` preserves interrupted
work internally and never licenses ordinary final delivery. `finalize` runs `deliver` after a
successful final freeze; run `deliver BUNDLE` yourself only after a manual `freeze`. Preserve
old bundles and engine snapshots unchanged. Within the standard scope, `unavailable` or
`exhausted` is an honest boundary when the remaining route would need a third preset or work
outside the lane checklists; name that route in `next_check`.

New decision review version 2 permits **zero** actions. A completed report cannot contain
an `investigate` action: feasible checks belong to execution; unavailable facts belong to
the findings/coverage with their evidenced boundary. Include a mitigation only when an
observed concern supports it, or a relevant explicit user requirement/use condition.
Do not manufacture action items merely to satisfy a template.

Finish with the completed assessment. Keep material uncertainty visible as **⚪ Unverified**
in the relevant conclusion, explaining why the evidence cannot currently be established.
Do not append 'useful additions', requests for ordinary exports, invitations to continue,
or a generic investigation backlog. A conditional fact that could change the conclusion
can be stated declaratively in the evidence section without assigning more work to the user.
Completion is about the performed scope, not a promise that every fact is knowable or safe.
